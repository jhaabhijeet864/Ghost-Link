# Phase 2: Connectivity & Mobile Observe - Research

## Overview

This phase focuses on establishing a secure, local connection between the Windows `LocalLoop` service and the new Flutter mobile app, alongside creating the initial "Observe Mode" UI.

Based on the requirements (MOB-01, MOB-02, MOB-05, NET-01, SEC-01) and design decisions (D-01 to D-18), the mobile app requires a domain-driven architecture, offline-first state cache using SQLite and Riverpod, and a robust Ed25519 WebSocket pairing and communication channel.

## Technical Implementation Details

### 1. Flutter Mobile App Architecture & Tooling (MOB-01)
- **Architecture**: Domain-Driven Design layout (`core/`, `domain/`, `data/`, `features/`).
- **State Management**: `flutter_riverpod` for responsive, decoupled state and dependency injection.
- **Local Persistence**: `sqflite` (or `drift` for type-safety) for storing the append-only event stream locally.
- **Secure Storage**: `flutter_secure_storage` to securely persist the mobile application's Ed25519 private key (D-04).
- **Routing & Deep Linking**: `go_router` combined with `app_links` or `uni_links` to handle the `localloop://pair?...` deep links seamlessly.

### 2. Secure Discovery & Pairing Sequence (SEC-01)
- **Windows C# Implementation**:
  - **QR Code Generation**: The `LocalLoop.Bridge` will render QR codes natively (e.g., using `QRCoder` in C#).
  - **Payload**: The QR code embeds an ephemeral token + local IP address + port in the deep link format (`localloop://pair?token=xyz&ip=192.168.1.5&port=8080`).
- **Flutter Implementation**:
  - **Cryptography**: Use the `cryptography` package in Dart to generate an Ed25519 keypair on first run.
  - **Pairing Exchange**: Upon scanning the QR / triggering the deep link, Flutter sends its Ed25519 public key to the Windows Service using the ephemeral token to authorize the exchange.
  - **mDNS Fallback**: Integrate `multicast_dns` for zero-conf IP rediscovery if the IP changes while on the same network (D-05).

### 3. Event Streaming Protocol (NET-01, MOB-05)
- **WebSocket Transport**: 
  - **Server**: C# `LocalLoop.Service` utilizes `System.Net.WebSockets` (or a wrapper) for pushing JSON-formatted events.
  - **Client**: Flutter utilizes `web_socket_channel` to maintain a persistent connection.
- **Authentication Header**: Dart signs a challenge (or standard payload) using its Ed25519 private key. C# verifies the signature against the stored public key for the paired device (D-14).
- **State Syncing ("Sync from Offset")**:
  - When Flutter connects, it sends its latest stored `EventID` (offset).
  - C# streams any events that occurred after that ID to catch the app up.
  - WebSocket pushes are immediately written to Flutter's SQLite database, which triggers a Riverpod provider to update the UI (D-17).

### 4. Observe Mode UI (MOB-02)
- Reconstruct views (logs, active workspace, agent status) purely based on the SQLite event store. 
- Global connection status manager: A Riverpod `StateNotifier` that tracks WebSocket connection state and displays an offline banner/icon when disconnected (D-18).

## Validation Architecture

To validate this phase automatically and ensure stability, the following testing and validation architecture will be used:

### 1. WebSocket & Protocol Mocking
- **Test Harness**: We will develop a mock C# WebSocket client in `LocalLoop.Tests` that can simulate connection drops, invalid signatures, and offset syncing without the full UI.
- **Flutter Mock Server**: We will create a local Dart-based mock server or use mocked `WebSocketChannel` instances in Flutter tests to stream predefined JSON events. This allows us to test the "Sync from Offset" and UI reconstruction behavior completely isolated from the Windows backend.

### 2. Flutter UI & State Testing
- **Widget Testing**: Leverage Flutter's `flutter_test` to simulate SQLite database inserts and assert that the Riverpod listeners accurately trigger UI rebuilds for Observe Mode screens (logs, status).
- **Golden Tests**: Capture visual regressions for UI states, especially the Global Offline Banner (D-18) and the QR code "Allow pairing?" prompt.
- **Deep Link Mocking**: Test the pairing sequence in Flutter by directly passing synthetic `localloop://pair?...` URIs into the router without needing an actual camera scan.

### 3. Integration Testing
- **Crypto Compatibility Test**: A dedicated test suite ensuring that signatures generated by the Dart `cryptography` package are successfully validated by the C# `.NET` cryptographic libraries (e.g., `NSec.Cryptography` or `System.Security.Cryptography`).
- **End-to-End Local Loopback**: A script that runs the C# service on `localhost` and a headless Flutter integration test that completes the pairing handshake and synchronizes events over the loopback interface.
